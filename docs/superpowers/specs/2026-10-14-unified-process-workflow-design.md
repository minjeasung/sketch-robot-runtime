## 1. 목적과 선택한 접근

사용자는 도장·뿜칠의 1–3단계 흐름과 용접의 대상 선택 화면에 집중된 기능을
같은 시스템으로 이해하고 조작하기를 원한다. 공통 단계를 다음과 같이 정한다.

1. **대상 인식**: 작업물에서 평면 또는 용접심 후보를 찾는다.
2. **작업 지정**: 후보 중 실제 작업할 영역 또는 심을 정한다.
3. **계획·실행**: 경로 입력과 공정 조건을 확인하고 계획을 생성·검사한 후 실행한다.

공통 화면과 상태 표현을 두고 공정별 입력·계획·실행 로직을 연결하는 방식을 선택한다.
검증·실행을 나눈 4단계는 화면 이동이 늘고, 공정별 독립 화면은 사용법이 달라지므로
이번 범위에서는 채택하지 않는다. 단계별 클릭 수나 입력 형식까지 같게 만들지는 않는다.

## 2. 현재 코드와 차이

- `web/index.html`의 단계는 `target`, `work_area`, `path`다. 표시 이름은
  대상 선택 / 작업영역 / 경로·실행이다.
- `web/js/app.js`는 도장·뿜칠의 단계, 영상 좌표계, 경로 입력과 실행 조건을 관리한다.
  수동 경로와 자동 채우기는 기존 요청을 발행하고 백엔드 경로 상태를 기다린다.
- `web/js/weld_workflow.js`는 `target` 이외 단계 선택을 막고, 대상·심 선택·계획 버튼을
  한 화면에 표시한다. 기존 평면 후보 컨테이너에 심 목록도 그린다.
- `web/js/process_settings.js`는 공정별 서버 설정과 로컬 미적용 편집을 구분한다.
  도장·뿜칠은 읽기 전용이고 용접만 설정 적용 명령을 제공한다.
- 도장·뿜칠의 `plan_validated`와 용접의 `READY`는 같은 검증 범위를 뜻하지 않는다.
  공통 화면이 이 차이를 감추거나 없는 사전 검증을 완료로 표시해서는 안 된다.

## 3. 단계별 동작

| 단계 | 도장 | 뿜칠 | 용접 |
|---|---|---|---|
| ① 대상 인식 | 대상 표시, 평면 후보 선택, 기존 D405 측정 | 대상 표시, ZED 평면 후보 선택·확정 | 대상 표시, 시험 심 불러오기 또는 외부 심 추출 요청 |
| ② 작업 지정 | 측정한 면의 도장 영역 확정, 기존 영역 정밀 측정 | 확정한 면의 분사 영역 확정 | 심 선택, 실행 순서, 진행 방향 지정 |
| ③ 계획·실행 | 수동/자동 경로 입력, 힘 설정 확인, 계획·검사, 영점 승인, 실행 | 수동/자동 경로 입력, 이격·폭·겹침·속도 확인, 계획·검사, 실행 | 설정 적용, 심 기반 토치·위빙 계획·검사, 실행 |

### 3.1 대상 인식

세 공정 모두 ZED 원본 영상에서 대상을 지정한다. 평면과 용접심 후보 추출의 기존
요청 식별자·영상 stamp·generation 처리를 유지한다.

- 도장: 선택한 면의 기존 측정 절차가 완료되어 다음 단계에서 사용할 표면을 확보한다.
  측정에 로봇 이동이 포함되는 현재 안내와 실행 차단 조건을 유지한다.
- 뿜칠: D405 이동 없이 ZED 평면을 확정한다.
- 용접: 현재 대상 요청과 일치하는 유효한 심 목록을 수신한다. 이 단계에는 후보 수와
  입력 출처를 표시하고, 실행 심의 선택·순서·방향 편집은 2단계에 둔다.

Fixture 제공자는 `시험 용접심 불러오기`, external 제공자는 `용접심 추출 요청`을
유지한다. 등록된 시험 심을 영상에서 추출한 결과로 표현하지 않는다. 대상 스케치를
토치 경로로 사용하지 않는다. 후보 없음·입력 거부·수신 대기는 서로 다른 상태다.

### 3.2 작업 지정

도장·뿜칠은 기존 `wall_front` 영상과 해당 좌표계의 영역 스케치를 사용한다.
도장의 미지정 영역 전체 사용 정책과 뿜칠의 닫힌 경계 요구는 기존 동작대로 명시한다.
활성 평면 변경과 다중 평면 측정 대기 조건도 유지한다.

용접은 별도의 심 목록 컨테이너에서 다음을 편집한다.

- 선택 여부, 심 ID, 길이와 좌표계, 자세 정보 유무.
- 선택한 심의 실행 순서와 정방향/역방향.
- 적용된 선택과 서버 응답 대기 상태.

용접 2단계에서는 자유선·직선·사각형 그리기와 스케치 지우기/되돌리기를 숨긴다.
ZED 영상은 대상 참조용이며 심 목록을 조작한다. 이번 변경에 심의 2D 영상 투영이나
새 3D 뷰어는 포함하지 않는다. 심 선택을 영상의 선 선택처럼 표현하지 않는다.

최소 한 개의 심이 서버에 적용되고 현재 대상·목록과 일치하면 3단계로 진행할 수 있다.
XYZ 심의 기준 자세가 아직 없더라도 3단계 설정에서 보완할 수 있으므로, 자세 부족은
계획 생성을 막는 조건으로 표시한다. 단순 화면 전환으로 선택을 재발행하지 않는다.
`다음: 계획·실행`은 현재 선택의 ACK/상태 적용을 확인한 뒤 이동하며 새 백엔드
확정 트랜잭션을 만들지 않는다.

### 3.3 계획·실행

공정 설정 패널, 경로 입력, 계획 결과, 실행 조건, 작업 시작 버튼을 이 단계에 둔다.

- 도장·뿜칠: `경로 방식: 자동 채우기 / 직접 그리기`를 선택한다. 초기값은 자동
  채우기다. 직접 그리기는 기존 경로 단계 스케치를 입력으로 사용한다.
- 용접: 경로 입력은 2단계에서 선택한 심이다. 선택 순서와 방향을 읽기 전용으로
  요약한다. 용접심과 별개인 자유 스케치 경로 입력은 제공하지 않는다.
- 공통 주 버튼은 `계획 생성·검증`이다. 선택한 경로 방식과 공정에 맞는 기존
  생성/계획 요청 하나만 발행한다. 현재의 자동 채우기·그린 경로 사용·용접 경로
  검증을 한 화면 동작으로 연결한다.
- 요청 중에는 중복 요청과 입력 변경을 막는다. 변경하려면 요청 결과를 기다리거나
  기존 중단 절차로 취소한다. 이전 요청의 늦은 결과로 새 계획을 승인하지 않는다.
- 도장·뿜칠의 공정 설정은 서버 값 확인용으로 유지한다. 용접 설정은 기존 적용
  ACK와 설정 revision 확인 후 계획을 요청한다. 미적용 편집이 있으면 실행을 막는다.
- 계획 요청으로 작업을 시작하지 않는다. `작업 시작`은 현재 계획과 실행 준비 상태를
  다시 확인하고 기존 실행 명령을 사용한다. 기존 실제/시뮬레이션 실행 확인 절차를 유지한다.

용접 계획은 생성과 검증을 한 요청에서 처리하므로 UI가 임의의 중간 생성 완료를
만들지 않는다. `계획 생성·검증 중`으로 표시하고, 성공한 결과에 대해서만 완료를 표시한다.

## 4. 검증 범위와 실행 준비 표시

3단계에는 다음 세 행을 각각 표시한다. 단일 녹색 배지로 세 상태를 합치지 않는다.

| 공통 행 | 완료 근거 | 완료가 뜻하지 않는 것 |
|---|---|---|
| 경로 생성 | 현재 작업 입력과 일치하는 서버 경로 결과 | 로봇 전체 궤적 사전 검증 |
| 계획 검사 | 공정별 백엔드가 현재 계획에 제공하는 검사 통과 | 미수행 검사, 실제 공정 품질 |
| 실행 준비 | 현재 런타임 상태·공정별 인터록·필요 승인 충족 | 실행 중 힘·추종 결과 보장 |

`계획 검사` 아래에 공정별 검사 범위를 항상 표시한다.

- 도장·뿜칠: 기존 경로·작업영역·공정 조건 및 executor의 현재 계획 수용 결과를
  표시한다. 이동 구간의 MoveIt 계획/충돌 검사가 실행 과정에서 수행되는 부분은
  `이동 구간 검사: 실행 중 수행`으로 구분한다. 기존 `plan_validated`만으로
  `전체 로봇 궤적 사전 검증 완료`라고 쓰지 않는다.
- 용접: 서버가 선택한 모든 심의 접근·진입·용접·이탈 궤적 계획을 받아들이고
  현재 identity의 READY를 반환했을 때 해당 사전 계획 검사가 완료되었다고 표시한다.
  실행 직전의 관절 시작 상태·장면·런타임 조건은 별도 실행 준비 조건이다.
- 로봇 없는 ZED 미리보기: 경로 생성까지만 완료 가능하다. 계획 검사는
  `로봇 검증 미수행`, 실행 준비는 `미리보기 전용`으로 표시하고 작업 시작을 제공하지 않는다.
- 검사 범위를 뒷받침하는 서버 상태가 없으면 `대기` 또는 `정보 없음`이다.
  시간 경과, 버튼 클릭, 목록 존재만으로 검증을 완료 처리하지 않는다.

도장은 영점 조정 승인과 실제 tare 완료를 구분한다. 준비 단계에서 안전하게 유예된
접촉 검사는 `실행 중 확인`으로 표시하고 접촉력 유지 완료로 표현하지 않는다.
뿜칠은 일반 분사 준비와 분사 OFF 이동 시험을 구분하며 모의 ACK를 만들지 않는다.
용접은 시뮬레이션 출력이라는 표시를 유지한다.

## 5. 이동·수정·무효화 규칙

현재 보고 있는 단계와 백엔드 작업 상태는 독립적으로 관리한다. 단계 탭을 보았다는
이유로 완료 처리하지 않으며, 이전 단계로 돌아가 내용을 확인하는 것만으로 계획을
폐기하지 않는다. 새 결과 수신 시 강제로 화면을 전환하지 않고 다음 단계 버튼을 활성화한다.

| 변경 또는 사건 | 처리 |
|---|---|
| 대상 스케치 편집·재추출·대상 generation 변경 | 기존 영역/심 선택 및 계획의 재사용 차단. 새 서버 결과에 맞춰 다음 단계를 재확정 |
| 영역 변경·다른 활성 평면 선택 | 해당 작업의 기존 경로·계획 무효화, 측정/확정 결과 대기 |
| 용접심 선택·순서·방향 변경 | 대상과 심 목록 유지, 기존 계획 무효화, 서버 적용 상태 대기 |
| 수동 경로 편집·경로 방식 변경 | 기존 계획 실행 즉시 차단, 새 계획 요청 필요 |
| 용접 설정 편집 | 미적용 상태부터 실행 차단. 적용 시 기존 revision 규칙으로 계획 무효화 |
| 연결 단절·서버 세션 변경 | 준비 완료 표시와 명령 대기 상태 해제, 이전 명령 자동 재전송 금지 |
| 장면·카메라 기준·시뮬레이션 reset 변경 | 기존 백엔드 무효화 범위에 따라 표면/심 또는 계획을 재확정 |
| 실행·중단 확인 중 | 입력·새 계획·새 실행 차단, 전역 중단 버튼과 진행 상태 유지 |

편집 즉시 생기는 로컬 차단은 서버의 늦은 READY로 해제할 수 없다. 새 요청에 대응하는
식별자와 ACK/상태가 일치해야 해제한다. 편집을 폐기하고 서버 적용값을 명시적으로
복원하는 경우만 기존 계획의 유효성을 다시 평가할 수 있다.

중단 버튼은 단계와 관계없이 접근 가능하게 유지한다. 단계 탭이나 화면 복귀가
중단·재시작·새 실행 명령을 발생시키지 않는다. 단계 접근을 막을 때는 필요한
선행 조건을 표시하고, 뒤 단계에서 문제가 생기면 수정할 단계로 안내한다.

## 6. 코드 구조와 변경 범위

기존 내부 단계 키 `target`, `work_area`, `path`와 ROS 토픽 계약은 유지한다.
표시 이름과 공정별 단계 내용을 통일한다.

- `web/index.html`, `web/sketch.css`: 공통 단계 제목·다음 단계 안내, 독립 용접심
  목록 영역, 경로 방식 선택, 3단계 결과·설정 배치.
- `web/js/workflow.js` 신규: 공통 단계 접근 조건과 화면 표시 상태를 계산한다.
  로봇을 직접 제어하거나 세 공정의 원시 ROS 상태를 하나로 합치지 않는다.
- `web/js/app.js`: 도장·뿜칠의 기존 상태/요청 함수를 공통 단계 화면과 연결한다.
  현재 좌표계, 경로/영역 입력, 다중 평면·접촉 인터록 처리는 보존한다.
- `web/js/weld_workflow.js`: 대상 요청·선택·설정·계획·실행 transport를 보존하고
  1단계 강제 고정과 평면 컨테이너 재사용을 제거한다. 공통 UI용 상태를 제공한다.
- `web/js/process_settings.js`: 3단계 배치와 미적용/대기 표시를 연결한다.
  서버값과 로컬 초안을 구분하는 기존 로직을 유지한다.
- `docs/WELDING_ISAAC.md`, `docs/SPRAY_MOTION_TEST.md`,
  `docs/RB20_PAINTING_ISAAC.md`: 실제 바뀐 단계와 검증 범위를 반영한다.

공통 UI 상태에는 공정, 현재 단계, 단계별 완료/대기/오류와 차단 이유,
경로 생성 상태, 계획 검사 상태·범위, 실행 준비·실행·중단 상태가 포함된다.
공정별 어댑터가 기존 식별자를 검증한 뒤 이 상태를 만든다. 도장·뿜칠의
path/hash/영역/generation과 용접의 session/revision/plan identity를 문자열 하나로
대체하지 않는다. 공통 UI 상태는 표시용이며 기존 백엔드 실행 검사를 대체하지 않는다.

이번 범위에는 새 ROS 공통 프로토콜, 전체 실행기 통합, 도장·뿜칠의 전체 궤적
사전 계획 기능, 분사/용접 하드웨어 어댑터, RL, 새 인지 알고리즘을 포함하지 않는다.

## 7. 수용 기준과 검증

1. 세 공정 모두 같은 3단계 이름을 표시하고, 용접도 1→2→3으로 진행할 수 있다.
2. 용접 1단계에는 대상·추출, 2단계에는 심 선택·순서·방향, 3단계에는 설정·계획·실행이
   표시된다. 2/3단계의 스케치 입력으로 대상이나 용접 경로를 덮어쓸 수 없다.
3. 도장·뿜칠의 수동/자동 선택은 각각 기존 요청을 한 번만 발행한다.
   영상 좌표계와 활성 평면 식별자가 보존된다.
4. 화면 단계 전환은 로봇 이동·새 요청·계획 무효화를 발생시키지 않는다.
   실제 입력 변경 시에는 늦은 이전 응답이 와도 작업 시작이 활성화되지 않는다.
5. 용접 선택 ACK 대기, 미적용 설정, 빈 심 목록, 자세 부족, 계획 실패를 각각 표시한다.
6. 생성 완료·계획 검사·실행 준비를 구별하고, 로봇 없는 미리보기는 실행할 수 없다.
   도장·뿜칠을 용접과 동일한 전체 궤적 사전 검증으로 표시하지 않는다.
7. 도장 영점 승인, 뿜칠 분사 OFF 모드, 용접 시뮬레이션 표시는 유지된다.
8. 실행/중단 확인 중 입력이 잠기며 연결 복구·늦은 ACK로 실행 명령을 재전송하지 않는다.
9. 단계·공정 전환 뒤 이전 공정의 버튼, 목록, 완료 배지가 남지 않는다.

기존 웹 harness에서 공통 단계 상태, 공정별 transport, 수정 후 늦은 응답,
연결 복구·중단 대기를 검증한다. 브라우저에서는 세 공정의 화면 배치·그리기 도구·
키보드 단계 조작·진행/차단 이유와 기존 미리보기를 확인한다. 실행 검증이 필요한
경우 기존 Isaac 프로파일로 수행하고 실제 로봇 구동을 UI 변경 검사에 포함하지 않는다.

2026-10-14 변경 전 관측값은 웹 91개 통과, Python 1,283개 통과·16개 실패다.
Python 실패는 기존 접촉 테스트 10개, 뿜칠 mock·카메라 소스 비교 2개,
9090 포트 점유 관련 API 4개였다. 이 기록은 새 변경의 통과 증거가 아니며,
구현 후 관련 검사를 새로 실행하고 신규 실패와 기존 실패를 구분한다.

사용자가 단계 배치, 단일 계획 버튼, 공정별 검증 범위 표시를 포함한 설계를 확정했다.

구현 계획 검토와 실행 방식 선택 후 제품 구현에 착수한다. 설계 확정만으로
제품 코드나 로봇의 실행 동작은 변경되지 않는다.
